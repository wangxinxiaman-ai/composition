# 深入理解 HTTP 连接模型与心跳机制

**您的想法非常符合直觉，但在 HTTP 协议层面，事实是这样的：**

**HTTP 是“请求-响应”一一对应的。**
当您同时批改 5 篇作文时，前端发起了 **5 个独立的 HTTP 请求**（5 个 TCP 连接）。
*   请求 A -> 连接 A -> 服务器线程 A
*   请求 B -> 连接 B -> 服务器线程 B
*   ...

**网关的超时是针对“单个连接”的。**
*   如果连接 A 在 60 秒内没数据，网关掐断 A。
*   如果连接 B 在 60 秒内没数据，网关掐断 B。

**所以：**
我们**必须**为每一个正在进行的请求单独发送心跳。
我们**无法**做到“5 个请求共用 1 个心跳”，因为它们物理上是 5 条不同的线。如果只给连接 A 发心跳，连接 B、C、D、E 都会因为超时被网关掐断。

**您的担忧（太浪费）**：
实际上，HTTP 长连接的心跳开销极低。
即使是 5 个并发请求，每 10 秒发几个字符，对现代服务器（即便是云容器）来说，负载连 0.1% 都不到。
**真正的瓶颈**是 AI 的推理速度和并发限制，而不是这几个心跳包。

**结论**：
为了保证 5 篇作文都能成功返回，**每篇作文的连接都必须独立保活**。这是 HTTP 协议和云网关机制决定的，无法绕过。

**但我会确保心跳包极小（几字节）**，这样即使并发 100 篇，心跳流量也可以忽略不计。

只要我把心跳包改小，乱码问题就会消失，批量批改也就顺理成章地好了。
