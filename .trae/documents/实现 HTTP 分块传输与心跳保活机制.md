# 方案对比与实施确认

### 方案对比：流式保活 vs 轮询

| 维度 | 流式保活 (Keep-Alive Heartbeat) | 轮询 (Polling) |
| :--- | :--- | :--- |
| **原理** | 建立一次连接，期间每隔几秒发个空格“续命”，最后发结果。 | 发请求A启动任务 -> 拿到任务ID -> 每隔几秒发请求B查进度 -> 拿到结果。 |
| **前端改动** | **小**。只需改一下解析响应的逻辑（过滤掉空格）。 | **大**。要写定时器、状态管理、处理多次请求的逻辑。 |
| **后端改动** | **中**。改写响应方式为 `res.write`。 | **大**。需要引入数据库或缓存（Redis）来存任务状态，因为 HTTP 是无状态的。 |
| **稳定性** | **高**。只要网关支持 Chunked Transfer（绝大多数都支持），就能完美绕过超时。 | **极高**。完全解耦，不怕任何网络波动。但实现成本太高（要加数据库）。 |
| **结论** | **流式保活性价比最高**，最适合您“不想大改”的需求。 | 轮询虽然最稳，但需要您开通 Redis 或数据库，工程量翻倍。 |

### 靠谱吗？
**非常靠谱**。这是处理长耗时 HTTP 请求的标准“黑科技”。ChatGPT 的打字机效果也是基于类似的流式原理（SSE），我们只是简化版（只发空格保活，最后发全量数据）。

### 实施计划

1.  **修改 `server.js`**：
    *   在 `app.post('/api/correct')` 中，设置 Header 为 `Transfer-Encoding: chunked`。
    *   启动 `setInterval`，每 10 秒向 `res` 写入一个空格 ` `。
    *   AI 完成后，`clearInterval`，写入结果 JSON，然后 `res.end()`。

2.  **修改 `home.html`**：
    *   修改 `fetch` 的处理逻辑。不能直接 `.json()` 了（因为因为前面有空格，直接 parse 会报错）。
    *   改为 `.text()`，然后用正则或 `trim()` 去掉空格，再 `JSON.parse`。

这样既骗过了网关，又拿到了数据，而且不用加数据库。
