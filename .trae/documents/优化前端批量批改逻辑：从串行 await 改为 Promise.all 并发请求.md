# 并发优化：从串行批改改为并行批改

**您说得非常对！**
目前的现象（第2篇比第1篇晚70秒，第3篇又晚112秒）清楚地表明：**现在的逻辑是串行的**（批改完一个，再批改下一个）。
这效率太低了。如果是并行调用，3篇作文的总耗时应该接近最慢那篇的耗时（约2分钟），而不是叠加（4-5分钟）。

**问题根源**：
前端代码（`home.html`）里的 `submitBtn.onclick` 逻辑里，用的是 `for` 循环加 `await`。
```javascript
for (let i = 0; i < students.length; i++) {
    // ...
    const resp = await fetch(...) // 这里 await 了，必须等上一篇回来才发下一篇
    // ...
}
```
这就是导致“排队”的罪魁祸首。

**优化方案**：
将 `for` 循环改为 `Promise.all`，**并发**发送所有请求。
这样 3 个请求会几乎同时发给后端，后端（如果是 Node.js）是非阻塞的，可以同时处理这 3 个请求（只要内存够）。

**风险提示**：
*   **并发限制**：如果并发太高（比如一次 50 篇），可能会瞬间打爆后端的内存（OOM）或者触发 API 的速率限制（Rate Limit）。
*   **当前场景**：您限制了最多 5 个学生，并发 5 个请求通常是安全的。

**行动计划**：
1.  **修改 `home.html`**：
    *   移除 `for` 循环里的 `await fetch`。
    *   改为创建一个 `Promise` 数组。
    *   使用 `Promise.allSettled`（比 `Promise.all` 好，防止其中一个失败导致全部失败）来等待所有结果。
2.  **更新 UI 逻辑**：
    *   原本是“正在批改：学生1...”，完成后变“正在批改：学生2...”。
    *   并发后，UI 需要显示“正在并行批改 3 位学生...”，或者显示进度条“已完成 1/3”。

**这改动很小，但体验提升巨大。**
我这就把前端代码改成并行的。
